# CEATS 团队协作规范（CONTRIBUTING）

> 对应软件工程实验 8：版本控制与团队协作
> 适用范围：Se_Lab 仓库的全部代码、文档与设计资源

---

## 一、分支策略（核心准则）

| 分支 | 定位 | 命名规范 | 规则 |
| --- | --- | --- | --- |
| `main` | 生产分支，存放可交付的稳定版本 | `main` | **禁止直接提交**，仅通过合并 `dev` 更新；每次合并需能通过全量测试 |
| `dev` | 集成分支，功能在此汇聚并做联调 | `dev` | 由 `feature/*` 合并进入，需保持随时可运行 |
| `feature/*` | 功能开发分支，一个功能一条分支 | `feature/模块名` | 基于 `dev` 创建，开发完成后合并回 `dev` |

本项目按模块边界切分功能分支，与系统设计的分层保持一致：

```
feature/database            数据层：建表、索引、CRUD、聚合查询
feature/recorder            业务层：成绩录入与输入校验
feature/analyzer-visualizer 业务层 + 展示层：弱项诊断与可视化
feature/scraper-kb          业务层：公告抓取与知识库
```

**禁止行为**：严禁直接在 `main`、`dev` 上编写功能代码；所有开发工作均在 `feature/*` 分支开展。

## 二、提交规范

### 2.1 提交信息格式

统一采用 `type(scope): 描述` 格式，`scope` 为模块名（可省略）。

| 类型 | 含义 | 示例 |
| --- | --- | --- |
| `feat` | 新增功能 | `feat(analyzer): 增加三维加权弱项评分算法` |
| `fix` | 修复缺陷 | `fix(analyzer): 未练习模块不再参与评分与排序` |
| `refactor` | 重构（不改变外部行为） | `refactor(database): 抽出公共联表查询片段` |
| `test` | 补充或调整测试 | `test(recorder): 补充用时解析的边界用例` |
| `docs` | 文档变更 | `docs: 补充 README 启动说明与目录结构` |
| `chore` | 构建、依赖等杂项 | `chore: 添加 requirements.txt` |
| `merge` | 分支合并 | `merge(dev): 合并 feature/recorder 到 dev` |

### 2.2 提交频率与粒度

- 每完成**一个可独立运行的小功能**或修复**一个 bug** 就立即提交，避免大量代码堆积；
- 单次提交的核心代码控制在 **100 行以内**，便于审阅与回滚；
- 提交前必须保证本地可运行：`python -m pytest tests -q` 全绿再提交。

### 2.3 不应提交的内容

- 本地数据与产物：`data/*.db`、`data/charts/*.png`、`.coverage`
- 环境与缓存：`__pycache__/`、`.idea/`、`.pytest_cache/`、`*.log`
- 任何密钥、Token、个人隐私信息

---

## 三、代码审查要求

1. **合并前提**：所有 `feature/*` 需通过 Pull Request 申请合并至 `dev`，禁止直接使用 `git merge` 推送；
2. **审查流程**：PR 提交后由至少 1 名成员审查，确认逻辑合理、命名规范、无冗余代码后方可合并；
3. **审查重点**：
   - 功能完整性：是否覆盖需求编号对应的全部可验证标准；
   - 参数校验是否充分（边界值、非法输入）；
   - 命名与注释是否符合 PEP 8（见第五节）；
   - 是否与既有模块产生重复实现（同一能力不得有两个入口）；
   - 是否补充了对应测试用例。

---

## 四、冲突解决原则

1. **预防优先**：合并分支前必须先 `git pull` 目标分支最新代码，本地同步后再合并，减少冲突概率；
2. **解决规范**：冲突发生后优先在本地解决，**保留双方有效代码**，不得随意删除他人开发的功能模块；
3. **冲突标记处理**：完整删除 `<<<<<<<`、`=======`、`>>>>>>>` 三行标记，按业务语义合并内容，而不是简单二选一；
4. **回归验证（强制）**：解决冲突后必须执行全量测试 `python -m pytest tests -q`，
   确认无功能丢失后再提交；历史上曾因遗漏该步骤导致导入报错。

标准操作流程：

```bash
git checkout dev
git pull origin dev
git merge feature/analyzer-visualizer
# 出现 CONFLICT 后手动编辑文件，删除冲突标记并合并双方内容
git add README.md
git commit -m "merge(dev): 合并成绩录入与可视化说明，解决 README 冲突"
python -m pytest tests -q          # 回归验证，必须全绿
git push origin dev
```

## 五、代码风格约定

| 项目 | 约定 | 示例 |
| --- | --- | --- |
| 模块名 | 小写 + 下划线 | `database.py`、`visualizer.py` |
| 类名 | 大驼峰 | `RecordService`、`AnnouncementScraper` |
| 函数 / 变量 | 小写 + 下划线 | `parse_duration`、`seconds_per_question` |
| 常量 | 全大写 + 下划线 | `TARGET_SECONDS_PER_QUESTION` |
| 私有成员 | 前置单下划线 | `Database._conn` |
| 缩进 / 行宽 | 4 空格（禁用 Tab） / ≤ 100 字符 | — |
| 注释 | 模块与公开函数必须有文档字符串，说明参数、返回值与异常 | `:raises RecordError:` |
| 导入顺序 | 标准库 → 第三方库 → 自定义模块，每组内按字母序 | — |

架构约束（违反视为设计缺陷）：

- 依赖方向必须单向：**展示层 → 业务层 → 数据层**，禁止任何反向或跨层调用；
- SQL 只能出现在 `src/database.py`，业务层不得直接书写 SQL；
- 可调参数只能定义在 `src/config.py`，禁止在业务代码中出现魔法数字。

## 六、附则

1. **文件管理**：新增功能模块需单独建文件，文件名与职责对应，避免单文件过度冗余；
2. **文档同步**：功能变更时同步更新 README 与本规范对应的说明；
3. **本规范的执行**：规范内容随项目演进持续更新，重要变更需在 PR 中说明理由。
